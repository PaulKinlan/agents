### Why this is an acting defect, not just a reporting discrepancy

`sdk-host/host.mjs:85` writes the SAME `host_pid` into every SDK lane state; when one lane stops, its socket is closed/unlinked at `:275` BEFORE `host_pid` is nulled and saved at `:309`. Deployed `remote/reaper.mjs:117` took `kill(host_pid,0)` as proof EVERY state file's lane was live. At `:180` it therefore changed a detached `FLEET_LANE`-tagged job from `orphan:true` to false. A browser at **12 minutes** should hit the **10-minute orphan-browser rule** (`:218`), but a mislabelled non-orphan must wait for the **45-minute generic browser rule** (`:219`). In the isolated dry-run, one synthetic 12-minute browser process-table row for an actual *inert `sleep` PID* tagged to that lane produced **0 would be killed** with stale SDK state/live shared PID/no socket and **1 would be killed: KILL orphaned browser (12 min, nobody will close it)** when only that stale state was removed (`/tmp/agents-f6du-hs4i-reaper-probe.log`). This is not a real browser or a live kill.

This patch makes only SDK lane membership of `liveLanes` require a valid numeric shared PID **and a connectable per-lane Unix listener**; the non-SDK PID path is left unchanged. A socket pathname with no listener is not evidence; a missing/refused listener is definite enough to apply orphan rules. A saturated listener / one-second connect deadline remains *possibly live* and **protects work**. Importantly, permission/resource/other ambiguous probe errors also protect work rather than authorising a KILL. On this VM a local socket mode-000 probe produced `ERROR=EACCES` (`/tmp/agents-f6du-j8f4-probe-eacces.log`), and the focused test's corresponding restricted-listener case stays no-kill. The separate hs4i **status** patch can report a failing probe as stopped to trigger a recoverable start; the reaper cannot make the same error-policy choice because killing is irreversible.
